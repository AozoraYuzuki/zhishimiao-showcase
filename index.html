1

AI 工具不可能被诱导越权

大模型能伪造参数，但不该能伪造身份

问题
AI 客服挂了 list_my_orders、list_my_coupons 这类"查我自己数据"的工具。如果 userId 由模型传参，用户只要在对话里说 "帮我查一下 1002 号用户的订单"，模型就可能照做 —— 变成一条绕过鉴权的越权通道。
方案
工具签名里根本没有 userId 参数，它由服务端从登录态注入，模型能控制的只有业务参数 （关键词、分页等）。同时维护工具白名单，非白名单工具直接拒绝并记警告日志。
证据
service/ai/AiToolRegistry.java —— 工具执行入口的签名即 execute(Integer userId, String name, String argsJson)， userId 不在模型可控的 argsJson 里。
AiToolRegistry.java 工具注册与执行 
// 工具签名里没有 userId —— 模型无法伪造，天然防越权
"list_my_orders",  (userId, args) -> safe(() -> listMyOrders(orderService, userId)),
"list_my_coupons", (userId, args) -> safe(() -> listMyCoupons(couponService, userId)),

public String execute(Integer userId, String name, String argsJson) {
    if (!HANDLERS.containsKey(name)) {
        log.warn("[aiTool] 拒绝非白名单工具：user={} tool={}", userId, name);
        return errorJson("不允许的工具");
    }
    // userId 由调用方（服务端）传入，不经过模型
    return HANDLERS.get(name).apply(userId, argsJson);
}

2

订单并发一致性：状态机 + 原子条件更新

支付回调和超时关单同时改一个订单，谁赢由数据库裁决

问题
用户点支付的瞬间，超时关单任务可能也在跑，两个线程同时读到订单是"待支付"。 如果用"先查再改"，两边都会判定合法、双双写成功 —— 结果就是已支付的订单被误关，用户付了钱订单却取消了。
方案
状态机的每条合法流转都对应一条自带"当前状态"条件的原子 UPDATE， 靠影响行数判断胜负：0 行说明状态已被别人改过，本次操作直接失败。 库存同理，用 stock >= qty 条件更新防超卖。
证据
mapper/OrderMapper.java 里 7 条流转方法（markPaid / markShipped / markFinished / markCancelled / markRefunding / markRefunded / markRefundRejected）， 每条 SQL 都带状态条件。
OrderMapper.java · ProductMapper.java 条件更新 
-- 支付：只有当前确实是"待支付"才更新；已被超时关单则影响 0 行
update orders set status = 1, pay_time = now()
where id = #{id} and status = 0

-- 超时关单：同样要求当前必须是"待支付"
update orders set status = 4, cancel_time = now()
where id = #{id} and status = 0

-- 扣库存：条件里带 stock >= qty，从 SQL 层面堵死超卖
update tb_product
   set stock = stock - #{quantity}
 where id = #{productId}
   and stock >= #{quantity}

3

RAG 三模式检索 + RRF 排名融合

两路召回的量纲完全不同，所以只用排名、不用分数

问题
纯关键词检索召回差 —— 用户换个说法就搜不到；纯向量检索对精确词（菜名、规格）又不准。 而两路分数量纲完全不同：关键词是整数权重累加，向量是 0~1 余弦相似度。 直接加权求和得靠人工标定缩放系数，语料一变就失准。
方案
实现关键词（中文 2-gram + 标题加权）、向量（余弦相似度）、混合三种检索模式； 混合模式默认用 RRF 倒数排名融合 —— 只看排名不看分数， 天然免标定、对分数分布不敏感。另带降级链：向量不可用时自动退回关键词检索。
证据
service/ai/rag/RankFusion.java —— score(d) = Σ 1/(k + rank_i(d))，平滑常数 k 默认 60。
RankFusion.java reciprocalRankFusion 
// 只需排名，不需要跨路校准分数 —— 关键词与向量分数不同量纲也能融合
for (List<String> ranked : rankedLists) {
    int rank = 1;
    for (String id : ranked) {
        // RRF：同一片段在多路出现则得分累加
        fused.merge(id, 1d / (smooth + rank), Double::sum);
        rank++;
    }
}

关键链路

把"一次下单"拆开看

下面四张图分别回答：请求怎么走完整个链路、钱和超时同时到来时谁说了算、 订单状态怎么流转，以及 AI 客服怎么取数作答。

入口与事务边界

token 在 axios 拦截器统一注入；createOrder 标在事务内，购物车校验、优惠券核销、订单落库同生共死。

闸门与幂等

先校验地址与购物车是否为空，再按勾选项取数；删除已选购物车项按影响行数判断，避免重复提交造成重复扣减。

扣减与风险

扣库存走 stock >= qty 条件更新；下单成功即向 Redis ZSET 写入延迟关单任务。

竞态怎么产生

支付回调和延迟队列里的关单任务可能在同一时刻操作同一笔订单，两边都认为订单还是"待支付"。

怎么裁决

两条 UPDATE 都带 and status = 0，数据库保证只有一个能影响 1 行，另一个必然 0 行并失败退出。

Redis 挂了怎么办

关单不只依赖 Redis 延迟队列 —— 另有每 10 分钟扫库的对账任务补漏，以数据库为准，避免丢条目导致永久漏单。

状态与终态

待支付 / 已支付 / 已发货 / 已完成 / 已取消 / 退款中 / 已退款；其中已取消、已完成、已退款为终态，不可再流转。

流转靠白名单

枚举里用一张 TRANSITIONS 表声明"当前状态允许去向哪些状态"，canTransition 统一校验。

退款可撤销

退款中记录原状态，驳回时恢复回已支付或已发货，而不是简单丢弃 —— 回滚路径也是设计过的。

两条链路分工

库存、订单、优惠券这类实时数据走工具调用查库；菜谱、平台规则这类静态知识走 RAG 检索增强。

循环有上限

工具调用循环设 3 轮上限并强制作答，防止模型在工具之间反复横跳造成死循环与超额调用。

流式输出

通过 SSE 把回答逐字推给前端，实现打字机效果；服务端需关闭响应缓冲，否则会攒成一坨再返回。

工程与安全

🧪测试与质量

  • 65 个测试类、580+ 用例，JUnit 5 + Mockito + MockMvc，覆盖 Service 与接口层
  • Flyway 管理 20 个迁移版本，表结构随应用启动自动演进，不靠手工 SQL
  • 多环境配置分离，local / prod 各自独立，生产缺失密钥直接启动失败
  • springdoc / Swagger UI 生成接口文档，本地环境可直接调试验证

🔐安全实践

  • 授权默认拒绝，Spring Security 逐条放行，新增接口不会"忘记加鉴权"
  • JWT 无状态认证 + 黑名单吊销，退出登录后旧令牌立即失效
  • 越权防护：查询一律带 userId 条件，AI 工具的 userId 由服务端注入
  • 登录与找回密码 IP 维度限流、密码全量 BCrypt、支付回调 HMAC 验签、上传文件魔数校验

⚙️工程规范

  • DTO 入 / VO 出，实体不进 Controller，接口契约与数据库结构解耦
  • 构造器注入替代字段注入，依赖关系显式、便于测试
  • 全局异常处理，业务异常统一转换成标准返回体与错误码
  • Docker Compose 一键起 MySQL / Redis / 应用，含健康检查与依赖顺序
